Momento 2 · Fundamentos 03 / 06

HTML, CSS y JavaScript
cada uno con su rol

La separación clásica: qué hay en pantalla, cómo se ve y cómo reacciona.

HTML — estructura

Semántica + accesibilidad

  • Etiquetas con significado: <header>, <main>, <nav>, <article>
  • Botones reales (<button>) con foco visible y aria-label
  • SEO: metadata en app/layout.tsx + sitemap.ts + robots.ts
  • lang="es", contraste alto, navegación por teclado
CSS — estilo

Tailwind + responsive

  • Utility classes: flex, grid, gap-4, md:grid-cols-2
  • Tokens propios: bg-canvas-base, accent-cyan, shadow-glow-cyan
  • Mobile-first: breakpoints sm / md / lg
  • Glassmorphism: clase .glass con backdrop-blur
JavaScript — lógica

Eventos, fetch, validación

  • Eventos: onClick tilda un ítem y dispara re-render
  • async/await + fetch('/api/...') para pedir/guardar datos
  • Validación con Zod (formularios + payloads de API)
  • Módulos ES6: import / export entre archivos
Asincronía: sin await, el código sigue antes de que la respuesta llegue → renderizo con datos vacíos. Con await, espero la respuesta y recién después actualizo el UI.
Momento 3 · React 04 / 06

React: componentes que reaccionan

Toda la UI es una función que recibe datos y devuelve JSX. Cuando los datos cambian, la función se vuelve a ejecutar y React actualiza la pantalla.

Componentes + props

Funciones que reciben datos

  • Componente: función que retorna JSX (HTML escrito en JS)
  • Props: datos que el padre le pasa al hijo — solo lectura
  • Ej: <ItemCard item={...} onToggle={...} />
  • Composición: páginas grandes hechas de componentes chicos reutilizables
State + re-render

useState · datos que cambian

  • State: datos internos del componente que SÍ cambian
  • Cuando llamo setX(...), React re-ejecuta el componente
  • Ej en ListView: el set de ítems tildados es state
  • El SummaryHeader recalcula los rings en cada toggle
useEffect

Efectos secundarios

  • Corre después del render — para tareas que no son JSX
  • Casos típicos: pedir datos, suscripciones, timers, listeners
  • Tiene array de dependencias: [items, weekStart]
  • Si el array no cambia, el efecto no vuelve a correr
¿Cuándo re-renderiza?

Regla mental simple

  • Cambia el state del componente → re-render
  • Cambian las props que recibe → re-render
  • Re-renderiza el padre → re-renderizan sus hijos (por defecto)
  • React calcula la diferencia y actualiza solo lo necesario en el DOM
Momento 3 · Next.js · Momento 1 · CI/CD 05 / 06

Next.js + deploy a Vercel

Next.js organiza la app por carpetas y separa lo que corre en el servidor de lo que corre en el navegador. Vercel toma el código de GitHub y lo publica solo.

App Router

Carpetas = rutas

  • app/login/page.tsx → /login
  • app/app/list/page.tsx → /app/list
  • app/api/feedback/route.ts → POST /api/feedback
  • Layouts compartidos por sub-árbol (layout.tsx)
Cliente vs servidor

Dónde corre cada cosa

  • Server Component (default): traen datos de Supabase, render en servidor, llegan como HTML al navegador
  • Client Component ('use client'): usan useState, eventos, ejecutan JS en el navegador
  • Las API keys se quedan en server — nunca llegan al bundle del navegador

Momento 4 · Uso fundamentado de IA 06 / 06

IA como copiloto, no como autor

Yo diseñé el producto, partí el trabajo en fases y validé cada cambio. La IA escribió código a partir de prompts dirigidos — pero la arquitectura, las decisiones y la prueba son mías.

Herramienta + estrategia

Claude Code (Anthropic)

  • Elegida por su capacidad de leer el repo entero y razonar con contexto largo
  • Trabajo dividido en 10 fases (P0–P9), cada una con un prompt propio
  • Una fase por vez: criterios de aceptación claros antes de avanzar
  • Stack lockeado en CLAUDE.md — la IA no introduce dependencias por su cuenta
Cómo validé

Cada cambio se prueba

  • npm run lint + npx tsc --noEmit en cada paso
  • Probar el flujo en el navegador (npm run dev) — no solo "compila"
  • Vitest para lógica crítica (optimizador, parsers)
  • Lectura crítica del diff: si no entiendo una línea, la cuestiono
Errores reales detectados

Limitaciones que tuve que corregir

  • Edge cases de fechas (semanas que arrancan domingo) mal manejados
  • Tipos de TS demasiado laxos (any) — los reforcé con Zod
  • Lógica de matching producto → comida que dejaba pasar falsos positivos
  • Una redirect inicial apuntaba a /design-system en vez de /login
Documentación de prompts

Trazabilidad del trabajo con IA

  • 10 prompts versionados en docs/agent_prompts/00_…09_*.md
  • Cada uno con: objetivo, archivos a tocar, criterios de aceptación
  • Plan general en docs/implementation_plan.md
  • Reglas globales (estética, stack, RLS) en CLAUDE.md
